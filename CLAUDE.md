# Category-Agnostic P2P Rental Marketplace

UK peer-to-peer rental marketplace. Launch category is DIY tools and garden equipment, but the engine is category-agnostic — categories, fees, attributes, radii, deposits and policies are versioned configuration, never code.

**The specification is `docs/Category_Agnostic_Peer_to_Peer_Rental_Marketplace_BRD_v1.2.md`.** It is normative. v1.1 is superseded and kept only for audit. When this file and the BRD disagree, the BRD wins — and tell me, because one of them needs fixing.

**Read `docs/HANDOFF.md` before doing anything else.** It is the master handoff — current state, what to do next, external account status, product-owner tasks and open questions. `docs/` is **gitignored**, so nothing in version control points at it and a session that reads only the tracked files misses all of that. Per-phase detail lives in `docs/phase-NN-*/HANDOFF.md`, one folder per BRD §14 phase, each holding that phase's scope checklist, exit gate, slices, gaps, tech debt and session log. Cross-cutting engineering lessons are in `docs/LESSONS.md`, and the security posture, gap list and sequencing are in `docs/SECURITY.md`. Keep the master short and put phase detail in the phase folder.

**Before changing anything that looks odd, check `adr/`.** Several decisions here look like overengineering until you know the constraint behind them — why money splits use `allocate` rather than `multiply`, why a rental "day" is not 24 hours, why the brand name lives in one file. The ADRs record what was rejected and why. If you still disagree after reading, supersede the ADR rather than quietly changing the code.

Team is two people: one product owner (non-coder) and Claude as the engineer. There is no other dev team, no QA team and no budget. Optimise for correctness and low operating cost, not for scale we don't have.

## Operating discipline

Work one vertical slice at a time, within the approved phase only. Before writing code, restate: the slice, affected modules, data changes, API contract, tests, and security considerations. After the slice is green, produce the completion report (BRD §15.1) and **stop for approval**. Do not roll into the next slice.

A slice is not done until UI, API, database, permissions, error handling, monitoring and tests are all connected. No dead controls — every tab, button and link either calls real API behaviour or is visibly feature-flagged.

Write tests alongside implementation. Reproduce every bug with a failing test before fixing it. Never bypass tests, linting, migrations, permissions or CI to make something look finished.

## Invariants — never violate these

**Money.** Integer minor units (pence) plus an ISO 4217 currency code on the same record. Floats for money are banned in the database, API contracts and business logic. Rounding lives in the pricing service only.

**Time.** Store UTC. Render and calculate rental periods in the booking's stored IANA timezone (`Europe/London` at launch). Daily rates, due times and late fees must be correct across BST transitions.

**Configuration.** Never hard-code category names, fee percentages, radii, deposit bands, status labels, minimum values or provider credentials. If it might change without a deploy, it is configuration.

**Module boundaries.** No direct cross-module database writes. Modules talk through application services, interfaces or domain events. Modules are listed in BRD §5.1. **`pnpm invariants` checks this from session 43** — `no-cross-module-database-writes` maps every Prisma model to an owning `apps/api/src/<module>/` and flags a write verb on another module's table.

**Providers.** Every external provider gets an interface, a production adapter, a test fake, and an explicit timeout/error strategy. Never import a provider SDK outside its adapter. **`no-provider-sdk-outside-adapter` checks this from session 43**, naming the exact file allowed to import each SDK; `apps/web` is out of scope deliberately, because Clerk's Next SDK is a framework integration (ADR 0015).

**Idempotency.** Every payment operation, webhook handler, notification send and state transition is idempotent. Webhook events and idempotency keys are persisted entities, not in-memory tricks.

**Ledger.** Immutable. Corrections are reversing entries. Never edit or delete a ledger row.

**Business logic placement.** Not in UI components, route handlers or ORM models. Domain and application services only.

## Normative mechanisms — implement as specified or raise an ADR first

These were chosen deliberately after research. Deviating silently is a defect.

- **Double-booking prevention** (§8.5.1): PostgreSQL `EXCLUDE` constraint with `btree_gist` over `listing_id WITH =` and a `tstzrange WITH &&`, scoped to calendar-occupying states. `REQUESTED` is deliberately non-blocking. **It is specified and not yet built** — there is no `bookings` table and no such constraint in any migration. `btree_gist` is installed and `pnpm db:verify` proves the constraint is _creatable_ against a throwaway table it drops again; Phase 4's first migration writes the real one. Do not read the passing `db:verify` line as a guarantee about our data.
- **Damage security timing** (§8.7.2): authorise at the collection window, never at reservation. The held amount is a hard ceiling — overcapture is unavailable to us. Aggregate everything into one capture. Read the provider's real expiry timestamp (`capture_before`); never assume a duration. Visa merchant-initiated re-auths hold 5 days, not 7. A failed hold means `SECURITY_FAILED`, never a silent unsecured handover.
- **Location privacy** (§8.4.1): one deterministic fuzz offset per listing, persisted at creation, minimum 500 m. Never recompute per request — that leaks the true point through averaging. Public APIs never return true coordinates pre-booking. Distances are bucketed.
- **Total price display** (§3.4.4): search results, listing cards, listing pages and quotes all show totals inclusive of mandatory fees. Drip pricing is a legal exposure, not a UX preference. Refundable damage security is shown separately and never folded into the headline.
- **Prisma + PostGIS** (§4.2): Prisma has no geography support. Keep `latitude`/`longitude` as ordinary columns so the model stays writable; maintain a **nullable** `Unsupported("geography(Point,4326)")` column by trigger; GiST index it; raw SQL for radius queries, confined to the Search & Location module behind a repository interface.
- **Notification channels** (§4.1): iOS web push only works for home-screen-installed apps. Push is supplementary. Every critical event must be deliverable by email or SMS, and a critical send with no non-push channel is a failure, not a silent success.
- **No platform-funded cover** (§8.15.1): never build an advertised cover amount, cover tier or damage guarantee funded by us. Substance beats labels — that is regulated insurance. Cover above the hold comes only from an authorised partner, from Phase 10.
- **Search filters compose, and an absent one is absent** (ADR 0046, §8.4): the category predicate lives _inside_ the radius query, because filtering after it is the filter-after-paginate bug; an unchosen filter contributes **no SQL at all** rather than an always-true clause, which is what keeps the unfiltered statement's **predicates and plan** identical to the one the Phase 3 gate was measured against (not its bytes — an empty fragment leaves the whitespace behind, and nothing rests on that). A search's **metric labels are closed unions and a filter is recorded as a boolean, never as the category** — a category is configuration, so labelling by it grows the series count through an admin form. **URL builders take the whole search**, so a new filter is a compile error in each rather than five call sites to remember. **Browse's form does mint `?category=`** and that is deliberate: the "All categories" option has an empty value, a plain GET form submits every named control, and a control a person operates needs a way to say _all_. The cost is **two URLs for every unfiltered search on our one indexable page, with no canonical tag until slice 2.12** — a known input to 2.12, not a defect in the form. Do not "fix" it by removing the option.
- **Keyword search is a filter and never a ranking input** (§8.4 as amended 16 August 2026, slice 3.3a): results stay **nearest-first** whatever words were typed. §8.4 requires ranking to be explainable — "nearest first, matching your words" is a sentence a person can be told, and a blended relevance-times-distance score is not — and `ts_rank` in the `ORDER BY` would replace the total order ADR 0045's paging depends on with a score that ties freely. A test fails if relevance enters the sort. The column is a **nullable `Unsupported("tsvector")` maintained by trigger from title (weight A) and description (weight B), GIN indexed** — deliberately the same shape as `listing_locations.fuzzedPoint`, so the schema has one pattern for a column Prisma cannot hold rather than two, and **nothing from `listing_locations` is in the index or may be added to it**. The query uses **`websearch_to_tsquery`, never `to_tsquery`**, because the latter _raises_ on input a person can type (`&`, an unbalanced bracket, two bare words) and that is a 500 on the most exposed route in the system. **A search term must never become a metric label or a log line** — a category slug is at least a set an administrator created, but a term is unbounded free text supplied by the public and can carry a name or an address, so it is recorded as a boolean like every other filter. Words matching nothing are an **empty page, not a 400** — the deliberate difference from the category filter, because an unknown slug describes a search we do not serve while unlucky words describe one we do.
- **Edge protection** (§10.2, added 3 August 2026): a filtering layer in front of all public traffic, and — the part that is normative and easy to undo — **the origin must not be reachable except through it**. A WAF that can be bypassed by dialling the origin directly is not a control, and the address is discoverable from historic DNS and certificate transparency. An outbound-only tunnel, or an edge-range allowlist **plus mutual TLS**; an IP allowlist alone is insufficient because it proves traffic came from the provider, not that it was sent for our zone. Automatic bans are time-boxed and self-expiring — a permanent one eventually excludes real users behind shared NAT with no route back — and every automated throttle or ban is audited and reversible.
- **Rate limiting is per account, and the address a caller claims is not trusted** (H7a, `docs/SECURITY.md` §2.1 and §4). The platform had no rate limiting of any kind until 20 August 2026. It now has a `RateLimiter` port, a Redis adapter reusing the API's one connection (`ioredis` stays in `main.ts`), a deterministic fake, and a guard applied **beside `AuthGuard` and always after it** — `decorated-routes.test.ts` reads every controller off disk and fails on a `@RateLimit` route that is not behind `AuthGuard`, because the guard allows when no account is present and such a route would be **silently unlimited**. **Fail-open is recorded per tier on the policy, never decided in the guard**; every tier allows on a store outage today and `'refuse'` exists unused for Phase 5. **The account id goes in the Redis key and the log line and never in a metric label** — a label outlives §10.1's erasure rules. **Three Redis commands rather than Lua**: `INCR` is already atomic, and `EXPIRE … NX` on _every_ request repairs a lost expiry where a first-increment-only script leaves a key that refuses that caller forever.

  **`/public/listings` is deliberately unlimited and an application-level per-IP limiter was refused rather than deferred.** The address is forgeable — `clientIpFrom` can only trust `X-Forwarded-For` behind a proxy we control, **which as of 24 August 2026 we finally have** — and per-IP keys are unbounded against a Redis running `maxmemory 192mb` with `noeviction` for BullMQ, so **forged addresses would fill it, stop writes, and take booking expiry down**. The limiter would be the attack. Per-IP belongs at the edge (§4 layer 1), and **the edge now exists** — so this is unblocked for the first time and is the next security slice rather than a deferral.

  **`TRUSTED_PROXY_HOPS` is `2` on staging from 24 August 2026, and it was measured rather than reasoned about.** Sending `X-Forwarded-For: 1.2.3.4, 9.9.9.9` from outside showed Cloudflare **appends** the caller to whatever the caller already wrote, and Caddy then appends `cloudflared`'s container address — so the app sees `1.2.3.4, 9.9.9.9, <caller>, 172.18.0.3` and `2` steps over the forged pair. `1` returns `cloudflared`'s own address; `3` returns `9.9.9.9`, **a value the attacker chose**, into `audit_logs.ipAddress`, which is _evidence_. **The default stays 0 — trust nothing — for local development and anything reached directly.** `docker-compose.app.yml` did not pass the variable to the web container at all until that day, so setting it on the box would have done nothing and said nothing: ADR 0017's predicted failure, one layer below where it was predicted.

- **Admin second factor** (ADR 0021, with the exception in ADR 0030): administrative access requires a second factor verified in the last 12 hours, and an absent claim fails closed. Clerk gates MFA behind a paid plan, so **`DANGEROUSLY_ALLOW_ADMIN_WITHOUT_MFA=true` opens the admin surface in local development only** — the API **refuses to start** with it set under `NODE_ENV=production`, it removes the second factor and never the role or suspension checks, and every admin page carries a banner while it is on. Buying Clerk Pro deletes the flag; do not weaken ADR 0021 instead.
- **Scheduled work: the schedule is the worker's, the work is the API's** (ADR 0048, 4.7a). The sweep writes `bookings` and `booking_events` and asserts a §7 transition, so it must run inside the API; the schedule belongs in `apps/worker`, which **cannot import any of it** — the worker is ESM to the API's CommonJS (ADR 0011) and has no database client. They cross over **`POST /internal/…` with `INTERNAL_TRIGGER_SECRET` in an `x-internal-trigger` header**, checked by `InternalTriggerGuard` — a separate guard, never an exemption inside `AuthGuard`, because an exemption is a branch in the one place that must never be able to say "no credential needed". **The secret is required in `loadEnv`, so an absent one stops both processes rather than opening the route**; the comparison is `timingSafeEqual` with lengths checked separately first; a refusal logs `absent` or `mismatch` and **never the presented value**. It authenticates a **machine and carries no identity** — nothing downstream may infer a user, a role or a permission, and anything a human should decide stays under ADR 0021. **`/internal/` is a reserved prefix naming its audience**, so the eventual edge rule is one line. Rotation restarts both services; there is deliberately no two-valid-secrets window. `docs/SECURITY.md` §2.6 carries the accounting.

  **From 4.7b the schedule exists**, and three things about it are easy to undo. **`upsertJobScheduler` against a _stable_ id** — registration runs on every restart, and `add({ repeat })` or a changed id leaves the old schedule running beside the new one, which is two sweeps a tick and invisible because both succeed. **Registration is fired, not awaited, and never fatal** — ioredis buffers while offline so awaiting hangs boot, and the container check boots the worker with no Redis and asserts it _keeps running_, so exiting would turn a broker blip into a restart loop. **The secret is kept out of logs by `SENSITIVE_KEY_PATTERNS`, not by omission at the call site**: `x-internal-trigger` is in that list because a `fetch` rejection can carry the request on `cause` and `redact` recurses into it. Do not "tidy" the header out of that list, and do not drop the `cause` to compensate — `preserve-caught-error` refuses it and it loses `ECONNREFUSED` with it.

- **A quote becomes at most one booking** (4.7a). `bookings.quoteId` is `@unique`. Without it a double-press or a second tab made two identical `REQUESTED` rows, and §8.5.1's `EXCLUDE` constraint **cannot see them** — §7.1 keeps `REQUESTED` out of the nine calendar-occupying states on purpose, so several renters may ask for the same dates. Plain unique rather than scoped to live states: re-using a dead booking's quote is re-pricing, which `Quote` already refuses by having **no `updatedAt`**. The adapter translates the violation, so a second tab reads a sentence rather than a 500.
- **A search's date filter is a predicate inside the radius query, and Search therefore reads two of Booking's tables** (ADR 0049, 4.9). A port answering _"which of these are free"_ can only be handed the rows **already paginated**, so it is the filter-after-paginate bug wearing a port's clothes — page one short, page two skipping listings nobody saw. It is a **predicate-only read, never projected** (ADR 0044's shape), the nine states come from `CALENDAR_OCCUPYING_STATES` and the date conversion from `periodFromLocalDates`, both imported rather than restated. **`REQUESTED` is not among the nine**: §7.1 makes a request non-blocking, so hiding a listing because somebody merely _asked_ would let anyone suppress a competitor by requesting their item and walking away. **An absent filter contributes no SQL at all**, so the undated statement stays the one 3.1c measured the Phase 3 gate against.

  **The dated one is measured now (4.9a), and its two halves are useless apart.** It came back at **p95 1945 ms against a 200 ms target** because a GiST index cannot answer `"startAt" < x AND "endAt" > y`, so Postgres seq-scanned `availability_blocks` and walked it once per candidate — 19.2M comparisons, caused by `ST_DWithin` estimating `rows=5` against a true 13,016. The fix is the composite **GiST index on `("listingId", "period")`** that `bookings` gets free from §8.5.1's `EXCLUDE` and this table never got, **plus** the predicate written as `"period" && tstzrange(…)`. Index alone 1429 ms, rewrite alone 1490 ms, **both ~250 ms**. **Do not "simplify" either back**, and note the rewrite is safe only because `block_period_is_present` and `booking_period_is_present` exist — a NULL `period` is invisible to `&&`, so a blocked listing would search as _free_. Both CHECKs are pinned by db tests. **`measure-search` still exits non-zero at 100 miles deliberately**: the product owner kept the 200 ms target rather than widening it (20 August 2026).

- **ADR 0046's compile-error promise stops at the parser** (4.9, found by using the product). Passing `ListingSearchQuery` whole makes a new filter a compile error in every URL builder — and it held for five builders and both ports. But `apps/web/src/app/browse/page.tsx` builds its `safeParse` input **field by field**, and zod parses `unknown`: a field that mapping forgets is not a type error, it is a filter that silently does nothing. The date filter shipped that way for the length of one manual check. **Wherever a typed object is built from untyped input, the type system is off duty.**
- **Identity** (ADR 0015): Clerk holds credentials; `users` is a **mirror** and `users.id` is the platform identity that every later foreign key points at. `clerkUserId` is an ordinary column, never a primary key. The **API is given only the JWT public key** — never `CLERK_SECRET_KEY` — which keeps session verification networkless and means a compromised API yields a key Clerk already publishes. The web app holds the secrets because Clerk's Next SDK requires it. Deletion is a soft delete with a tombstoned email; the ledger will reference these rows and can never lose a counterparty.

**A rental may not exceed its category's maximum duration, and 88 days is the ceiling rather than merely the default** (§8.5.3, 4.4a). Under the Consumer Credit Act 1974 a hire to an _individual_ that is **capable of subsisting** beyond three months is a regulated consumer hire agreement, and arranging those without FCA authorisation is an offence — "capable of subsisting" is what makes an _unbounded_ period the problem, whatever any single rental does. The cap is **versioned configuration on `category_versions`**, so a booking is judged against the cap it was made under. §8.5.3 permits a higher cap for business-heavy categories and **ADR 0043 refuses to let a business publish here at all**, so that case does not exist: the bound is enforced by a `CHECK`, by `maximumRentalDaysSchema` and again by `refusePeriod`, which takes the **lower** of the configured and statutory values. **`refusePeriod` has no override argument** — §8.5.3 makes the cap unoverridable by approval, so neither an owner nor an administrator can agree past it. Raising the ceiling requires a migration and an ADR, which is exactly the legal review §8.5.3 demands.

**An accepted booking rests in `ACCEPTED`, and accepting is a one-way door** (§7.1, 4.6a). §7.1 prescribes the acceptance transaction almost verbatim — _acquire the exclusive availability lock; move the accepted booking to `ACCEPTED`; and move every other `REQUESTED` booking whose dates overlap to `DECLINED`_ — and **the lock is acquired by the write itself, never by a query before it**: `ACCEPTED` is one of §8.5.1's nine calendar-occupying states, so the `EXCLUDE` constraint starts applying to that row the moment it lands. Checking availability first is the anti-pattern §8.5.1 names. **It rested in `ACCEPTED` for the length of Phase 4**, because §7's two onward states were `RESERVED` (_"payment secured"_) and `AWAITING_PAYMENT`, and neither had a payment flow behind it. **5.2c built that edge**: a renter moves their own booking `ACCEPTED → AWAITING_PAYMENT → RESERVED | PAYMENT_FAILED`, so the resting place is now a waiting room rather than a terminus — **but only where `booking.payment` is on, and it is off everywhere**, so the observable behaviour is unchanged until 5.2e. **The consequence still stands: an acceptance cannot be undone** — §7 gives `ACCEPTED` no cancel edge until `RESERVED` — so the owner's control must say so where the decision is made. That is a one-way door shipped deliberately with the sentence attached (product owner, 18 August 2026), not an oversight. **`auto-declined` is its own event type** because `bookingEventSchema` withholds `metadata` from a party: without it the losing renter reads _"declined"_ where §7.1 requires them to be told a conflict took the dates. **A decline is allowed after §8.6's deadline and an acceptance is not**, because the deadline exists so a renter is not held indefinitely.

**An accepted booking was invisible to both parties, and 4.8 closed it** (4.6b; 4.8a–d). It left the owner's requests panel the moment it was answered, 4.3b's calendar drew no booked periods, and a renter never had anywhere to look — 4.5b's confirmation was the only place a booking was ever shown to them and a reload lost it. **This paragraph called it "the largest hole in the product" for two days after 4.8d filled it**, which is the same failure as the sentence it sits beside: a claim that was true when written, in a file nothing fails on. Both dashboards, the calendar's booked layer and the §10.1 export section shipped in 4.8; **what is still missing is a page from which a renter can pay** — 5.2d.

**A booking keeps the terms it was made under, copied rather than joined** (§8.2, §6.2, 4.5a). The money, the item's name and its category's name are **written onto the booking row** at the moment it is made, from the quote it was made from — never read back through the listing. A booking that rendered its price through a join would show today's price for last month's hire, or nothing at all, because a listing may be repriced, retitled, paused, or collapsed to its district when its owner leaves. The booking also stores **the quote and the category version** it was priced under, so the copy is provable rather than merely asserted. **A booking is created directly in `REQUESTED` and nothing enters `DRAFT`** — §7's `DRAFT → ABANDONED` models a started-but-unsubmitted booking and the _quote_ already is that artefact, so a `DRAFT` row transitioned out of in the same transaction would be a state no human ever sees. **`booking_events` is append-only and a trigger enforces it**; §6.2 calls it an immutable state history, and a history that can be edited is evidence of nothing.

**A period costs the cheapest cover from the owner's own rates, and the platform sets no discount curve** (§8.5.2, ADR 0047, 4.4b). Not "whole weeks plus a daily remainder" — **the cheapest set of the owner's rate units that covers _at least_ the hire**. That framing is the decision: because anything covering `n + 1` days also covers `n`, the feasible set only shrinks as a hire lengthens, so **monotonicity is structural rather than tested-and-hoped**, and because plain daily is always feasible the price can never exceed the naive total. Decomposition charges **£60 for six days and £50 for seven** when the weekly rate is generous, which is a renter paying more for less time. The **weekend rate applies only to a hire that genuinely starts on a Friday, and once** — it is an occasion, not a quantity, and the narrow reading is the one that can be widened later without silently repricing every listing that has one. The renter fee is taken on the **whole period's** charge, never per day, or §3.4.2's £1 floor becomes £14 on a fortnight. **A quote pins the category version it priced under**, which is ADR 0042's commitment-time pin arriving a phase early, and **the duration cap is read from the _current_ version** because a cap is a rule about what may happen now rather than a meaning attached to stored answers.

**A date a person chose becomes an instant in exactly one place** (4.3b, extracted to `booking/local-period.ts` in 4.4b), in the platform's timezone. `YYYY-MM-DD` strings cross every wire and every page — the API's projections carry dates and never instants, pinned by a `strictObject` — because a conversion in the browser happens in whatever timezone the device is in, and that is wrong for seven months a year in a way no reviewer sees. `@platform/core` holds the six primitives it needs (`startOfLocalDay`, `addLocalDays`, `addLocalMonths`, `weekdayOf`, `formatLocalDate`, `formatLocalMonth`); **a `new Date('2026-08-20')` anywhere is midnight UTC and is the bug**. The wire's `endDate` is **inclusive** and the column's is not — "the 20th to the 22nd" ends at the start of the 23rd, which is what lets a hire follow a block with no gap. **`ListingOwnership` is the first port Booking declares and Catalogue answers**, and it returns a boolean so the calendar can never hold a collection address.

**Phase 5 — Marketplace payments and ledger. OPEN, 20 August 2026. Provider: Stripe Connect.** Four slices: **5.1** the ledger and the double-entry primitives, **5.2a** the payment port and the settlement maths, **5.2b** the `payment_intent` record, the pinned-fee-policy port and the Payments service, and **5.2c** the renter pays and the booking moves. **The whole payment path exists and is switched off**: `booking.payment` defaults false because there is no provider until 5.2e, and the flag refuses **before anything is written**, so turning it on is the whole of what 5.2e has to do. 5.1 contains **no payment provider by design** ([ADR 0051](adr/0051-the-ledger-is-the-record-and-the-provider-is-a-channel.md)). The balance rule is a **DEFERRABLE constraint trigger** firing at COMMIT; UPDATE **and DELETE** are refused, stricter than `booking_events` because §8.7 names deleting; corrections are reversing entries and a transaction is reversed at most once. **`ledger_accounts.identity` is a derived unique key rather than a composite unique on `(kind, ownerId, currency)`**, because Postgres treats NULLs as distinct and the composite would hold two platform accounts in one currency with the balance split between them — and it makes get-or-create an `upsert` on one unique column. **Prisma's `upsert` is a find followed by a create rather than an atomic `ON CONFLICT`**, so the adapter catches the unique violation and re-reads — the index makes the outcome safe, the catch makes the loser succeed. It passed locally and failed on CI, which is the honest shape of a race. **Both of `ledger_entries`' foreign keys are composite on `(id, currency)`**, so an entry disagreeing with its transaction or account about currency is unrepresentable rather than merely wrong. **§8.7.1's one-capture-per-booking is a partial unique index** on succeeded attempts, so failed retries may accumulate and a decline followed by a success is an ordinary evening. **Payments derives its own attempt key** from the booking and the count of failed attempts, so no caller invents one: two presses compute the same key and charge once, and only a failure mints a new one. **The order of operations is the design** — settle on paper before the provider is called, write the attempt before calling it, post to the ledger before updating the attempt, and move the booking to `AWAITING_PAYMENT` before any of it — each choice picking which side of a crash to lose. ADR 0051's finding is that an interface is _not_ what makes a provider switch cheap — the **card vault is a 4–12 week PCI-to-PCI migration and connected-account KYC does not port at all** — so the ledger being our record is what does. Adding an account kind or a transaction kind is done **with the flow that posts to it**.

**Phases 6–12 have not been started.** No messaging, handover protocol, reviews, disputes or reporting. What exists is a platform that knows who somebody is, protects what it knows about them, can be administered safely, lets an owner describe and publish an item for rent that the platform can independently hide, **shows that listing to a stranger with no account**, and **lets a stranger type a postcode, type what they are looking for, narrow by category, narrow to the dates they need it, and page through what is near them**. From Phase 4 an owner says which dates their item is unavailable and sees what is booked on it; a renter gets a firm expiring price, turns it into a request, and both parties then **see the booking** — the requests panel, both dashboards, the calendar's booked layer — while an unanswered request **expires on its own** and everything appears in a §10.1 data export. **It is still not a marketplace: nothing is photographed and no money moves.** But the first complete marketplace interaction without real money, which is what §14 asks Phase 4 for, happens end to end. **Five of thirteen phases are closed, a sixth is open, and counting them overstates progress** — 0 and 1 are scaffolding, 2 and 3 are one person describing an item and another finding it, and the ledger and §8.9's condition-evidence protocol are each larger than everything built so far.

## Branch protection

`main` requires a pull request, linear history and resolved conversations. Force pushes and deletions are blocked. **Nine checks** must pass before merge: `Format, lint and types`, `Unit tests and coverage`, `Build`, `Database invariants`, `Container image`, `Deploy rehearsal`, `Worker integration`, `Secrets and dependencies` and `Analyse` (CodeQL). Branches must be up to date with `main` before merging.

Adding a CI job does not make it blocking — the required-check list is repository configuration and has to be updated separately, or the new job runs advisory-only.

**Known gap, accepted:** `enforce_admins` is off. With a single maintainer that is a deliberate escape hatch, but it means every rule above can be bypassed by the person who merges everything. It makes bypass a deliberate act rather than the default, which is the most a solo repository can enforce against itself.

**A deploy now waits for CI, and merging therefore no longer reaches staging in seconds.** `Release` used to fire on the push to `main` and gate on nothing; because merges are squashed, the SHA that lands is a _new_ commit whose CI run is concurrent, and with `enforce_admins` off a direct push reached staging entirely unverified. `Release` now holds a **`ci-passed` job** that polls for a completed, successful CI run **on that exact SHA** and fails closed on absent, queued, cancelled or an API error. It fired for real on #118 — waited 5m 08s, published 8s after CI concluded. **Chaining `workflow_run` off CI was deliberately rejected**: a second-level `workflow_run` takes its SHA from the tip of the default branch, so it would deploy a different commit than was built whenever `main` moved, presenting as a successful deploy of code nobody built. Do not "simplify" the polling job into a chain.

## Structure

Monorepo, pnpm workspaces (`packages/*`, `apps/*`).

Exists today:

```
apps/web                Next.js 16 App Router. The only service the ingress reaches
apps/api                NestJS on Fastify. Health, readiness, correlation, Dockerfile
apps/worker             BullMQ. Maintenance queue, correlation across the boundary
packages/core           Money and time primitives
packages/config         Brand identity, environment validation (server and web)
packages/contracts      Shared API types with runtime validation
packages/database       Prisma schema, migrations, client factory
packages/observability  Logging, correlation IDs, error-tracking seam
packages/runtime        Process lifecycle — graceful shutdown, shared by both apps
infra/postgres          Database initialisation SQL
infra/compose           Deployment stack, shared ingress, provisioning runbook
scripts/                Stack verification, licences, invariants, hooks, deploy, logs
adr/                    Architecture decision records
```

`docker-compose.yml` at the root is the **local development** stack. `infra/compose/` is what gets deployed — it runs published images by immutable tag, never builds, and publishes no ports except the ingress. Do not conflate them.

**Both apps diverge from the workspace tsconfig, in opposite directions, and neither is drift.**

- `apps/api` is **CommonJS while everything else is ESM**. NestJS depends on legacy decorator metadata, and `module: NodeNext` is the only setting under which a CommonJS app can import our ESM packages at all. ADR 0011.
- `apps/web` uses **`moduleResolution: bundler`**, so its relative imports carry **no `.js` extension** — the opposite of everywhere else. Next ships no `exports` map, so `next/link` is unresolvable under NodeNext. ADR 0013.

Adding `.js` to a relative import in `apps/web` breaks the build; removing it anywhere else breaks the runtime. Read both ADRs before "tidying" either.

**This is not the Next.js most documentation and most training data describe.** `apps/web` is on **Next 16**, whose APIs, conventions and file layout differ from 15 and earlier in ways that do not announce themselves — code that looks idiomatic can be a version behind. Next ships its own docs inside the package: read the relevant guide under **`node_modules/next/dist/docs/`** before writing app code, resolving it from `apps/web` rather than the repository root, because pnpm may not surface `next` at the top level. Heed its deprecation notices.

That warning is here, in our own words, because **Next 16.3 wanted to write it into the repository itself** — it generates `apps/web/AGENTS.md` and `apps/web/CLAUDE.md` on every `next dev`, and Claude Code loads the latter as project instructions. It is switched off with `agentRules: false` in `apps/web/next.config.mjs`, which explains why: a dependency that authors agent instructions can revise them on any version bump, the change arrives on disk the next time somebody runs the dev server rather than in a reviewable diff, and it is obeyed before anyone notices. **Do not turn it back on to "keep the tree clean"** — that trades a reviewable instruction for an unreviewable one.

**The app stack runs for real** on the Hetzner CX23 against Neon (ADR 0037), deployed by `scripts/deploy.mjs` on 9 August 2026. **The observability stack joined it on 14 August** (slice H5) — Prometheus scraping the API, Promtail shipping logs to Loki, Grafana on loopback behind an SSH tunnel, ~219 MB for the four containers. It is a separate compose project, so an app deploy does not disturb it. **The Caddy ingress ran for the first time on 24 August 2026**, and the prediction standing here for a month — that it was _"the wrong shape"_ — was half right. It **was**: it held ports 80 and 443 and obtained its own certificates, which is not what sits behind an outbound-only tunnel. What survived is the part that mattered: **routing by `Host` header stays in the Caddyfile**, in version control, and Cloudflare's public-hostname list points every hostname at that one container. It now publishes **only `127.0.0.1:80`**, carries no 443, never runs ACME, and has `cloudflared` beside it behind a `tunnel` profile — the profile exists because the CI rehearsal brings the same file up with no tunnel to join, and **omitting it fails quietly**: Caddy comes up, nothing connects it to Cloudflare, and `docker ps` looks healthy. See `infra/compose/README.md`, corrected by every first real run.

**What it watches, so nobody builds a second one.** Beyond Node's own numbers, the API exposes `http_request_duration_seconds` by route template and status class (H1), and from slice 3.1f `listing_searches_total` by radius × outcome and `geocode_duration_seconds` by outcome. **From H6 the worker is scraped too** — `worker:9464`, served by Node's own `http` rather than a framework — exposing `queue_job_duration_seconds` by queue × job × outcome, recorded in `createJobProcessor` so every job type is measured without its author remembering to. **`Metrics` in `@platform/observability` is a domain-shaped port with one adapter — nothing else may import `prom-client`**, and every label vocabulary is a closed union rather than a string — **`QueueJobSample`'s two were `string` from H1 until H6 closed them, which is the drift to watch for**; a job name in particular is read back from Redis, so an unrecognised one collapses to `unknown` rather than minting a series: a series is created per label combination, held in process memory and exported to a scraper that has none of §10.1's retention or erasure rules, so **cardinality is a retention decision and a personal-data decision, not a formatting one**. Never put a postcode, an id or free text in a label. **There are still no alert rules** — this is observability, not monitoring, and nothing wakes anybody up. Two are worth writing: `geocode_duration_seconds{outcome="unavailable"}`, because a geocoder outage is served to a searcher as an ordinary empty page, and from H6 **`up{service="worker"} == 0`**, which needs no threshold because the worker has no inbound traffic of its own — a failed scrape means the process is gone or wedged.

**Two rules the observability run produced, both cheap to break.** **Never edit the box's git working tree** — H5's files were `scp`'d there to test them and the next deploy refused, correctly, because `ci-command.sh` checks out the release SHA and git will not overwrite local changes; copy to `/tmp` and merge with a second `-f` instead. And **variable substitution stops at the file compose parses**: a mounted config is bytes to compose, so `${APP_ENV}` inside `prometheus.yml` needs Prometheus's own `--enable-feature=expand-external-labels` plus the variable in that container's environment.

**Request path.** Browser → Caddy ingress → `web` → (server-side) `api` → Postgres/Redis. Only `web` joins the `edge` network; the API is not reachable from the internet, and CI asserts that. When a browser-facing API route is genuinely needed, add it deliberately.

`apps/web/src/app/api/webhooks/clerk` is the **one such route that exists**, added deliberately in slice 1.2: Clerk cannot reach the API directly, so the web app verifies the delivery's signature — it is where the raw unparsed body exists — and forwards the event inward. The API owns what the event means and is the only service that writes.

**`apps/web/src/proxy.ts` protects routes from session 43, and it is authentication only.** It was a bare `clerkMiddleware()` for months — attaching auth context and guarding nothing — so `/account`, `/admin` and `/listings` all answered 200 to anonymous visitors and drew their full page shell, `/admin/categories` disclosing the whole admin information architecture. **Four** literal prefixes now call `auth.protect()` — `/account`, `/admin`, `/bookings` and `/listings` — matched on **whole segments** so a future `/listingsomething` is not swept in. (This said _three_ until slice 5.2d read the file against `proxy.ts`: `/bookings` joined the list and the sentence did not.) **It does not check roles**: ADR 0021 keeps role and second factor at the API on every request, and a role check here would be a second place for the rule to live and the easier of the two to get wrong. **`createRouteMatcher` was deliberately not used** — it is deprecated in the installed Clerk SDK and slated for removal.

**Security headers ship from `apps/web/next.config.mjs`, and the CSP is `Report-Only` on purpose.** HSTS, `Referrer-Policy`, `nosniff`, `X-Frame-Options` and `Permissions-Policy` are enforcing; the content policy is not, because the app loads Clerk from a dev instance and Next injects inline styles, and a wrong enforcing policy breaks sign-in for everybody with **no test to catch it — there is no browser in CI**. A CI step asserts the headers through the real ingress and **fails if an enforcing CSP appears**. Move it to enforcing only after watching a browser console through sign-in, sign-up and an avatar upload. HSTS carries no `preload`: that is a one-way door in browser binaries, binding subdomains of a domain nobody has bought yet.

**`RouteTransition` keys its page fade on the _flow_, not the pathname, and that is a fix rather than a subtlety.** It wraps every page in `key={...}` so a CSS entry animation replays per navigation — which means React discards and remounts the subtree. Clerk routes its **whole** sign-in flow under one catch-all segment, so `/sign-in` — `/sign-in/factor-one` looked like a navigation: `<SignIn />` was thrown away mid-flow, a fresh instance re-pushed its step path _relative to where it already was_, and the URL grew a segment per attempt (`/sign-in/factor-one/factor-one/…`) while the card reset to the email step forever. **Nobody could sign in, there was nothing in the console, and it survived from session 38 to 18 August 2026.** `MULTI_STEP_PREFIXES` — `/sign-in`, `/sign-up`, `/account/email` — now keep one key while a component walks its own sub-paths, matched on whole segments so a future `/sign-in-help` is not swept in. Do not "simplify" it to the first path segment: that would stop `/hire/a` — `/hire/b` fading, which is the design. A step inside a page is not a navigation between pages, and only the second may remount anything.

**Clerk instance configuration is load-bearing and lives outside version control.** Staging and production must use **separate Clerk instances** — a shared one means a staging sign-up creates a production account. The provisioning list is in ADR 0015, and **every item on it fails silently if missed**, which is why it is repeated here:

- a custom **`email` session claim** — without it the API rejects every authenticated request;
- the **`fva` factor-verification claim** (ADR 0021) — without it, correctly-signed tokens carry no proof of a second factor and every admin page refuses everyone;
- a **webhook endpoint** and its signing secret, subscribed to `user.created`, `user.updated`, `user.deleted` **and the four `session.*` events** (ADR 0025) — without the session events the sign-in history stays empty and nothing errors;
- **`delete_self_enabled` off** (ADR 0018) — otherwise Clerk's own delete button bypasses the page BRD §10.1 requires, which explains what survives;
- **new-device alert emails left on** (ADR 0026) — they are the only suspicious-login alerting that exists until an email channel does.

The API is given only the JWT public key, never `CLERK_SECRET_KEY`.

| `node scripts/seed-search-load.mjs --count 50000` | Fill the local database with tagged, obviously fake listings — and, from 4.9, a booked and blocked calendar for them (`--booked-percent`, `--blocked-percent`) |

`measure-search` **reads the SQL out of `prisma-listing-search.ts` rather than
restating it**, so what it measures is what ships — and it refuses to run if the
adapter grows a parameter it does not recognise, rather than measuring something
else. Leave the load data out of the database when you are done: the eight
fixtures the handoff describes are what every other test and walkthrough assumes.

Unit economics, from slice 5.3a. Also not part of any suite, and for the same
reason — it reads the categories that actually exist and writes a document about
them:

| Command                                         | Does                                                                                                                                                                                |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm build && node scripts/unit-economics.mjs` | Regenerate `docs/unit-economics.md` — BRD §3.4.3's worked example per category. **Exits non-zero when any category's contribution margin at its minimum booking total is negative** |

**It imports the pricing model rather than restating it**, `measure-search`'s rule,
so it needs `pnpm build` first and refuses with a sentence saying so if `dist` is
missing. **The gate is judged at one booking per owner per month**, deliberately
the pessimistic level, because Stripe Connect's **£2 per active connected account
per month** is amortised across an owner's bookings — judging at a busier level
would pass by assuming the traction the gate exists to survive the absence of.

**Both categories fail it today** and that is a real finding, not a broken script:
`outdoor-gardening` is **−£0.23** at its £10 floor and needs 2 bookings a month to
break even; `power-tools` has **no minimum booking total or platform fee at all**,
so a £1 booking loses **£2.38** and never breaks even at any activity level. §3.4.3
says such a category may not be enabled for public booking, and **nothing yet
enforces that** — the gate is this script, not the product. That is slice 5.3b.

**Prisma is on 7, which is not what most documentation assumes.** `url` is banned from `schema.prisma` and lives in `prisma.config.ts`; the client needs a driver adapter; the generator emits TypeScript source, which is gitignored and regenerated on install. Migrations ship as their own image and run before the stack comes up. ADR 0014 records what the compatibility gate found and what was rejected.

Integration tests (`*.db.test.ts`, `*.redis.test.ts`) need `pnpm db:up` **and** `pnpm db:migrate:deploy` against the test database.

Coverage thresholds are enforced in `vitest.config.ts`: 90% lines, functions and statements, 85% branches, and cover `packages/*/src` and `apps/*/src` only. `scripts/` is outside them deliberately — its pure logic is unit tested under the `scripts` vitest project, and the parts that drive Docker are covered by the `Deploy rehearsal` CI job instead. `.nvmrc` pins Node 22; CI runs Node 24.

## Environment

Windows 11. PowerShell is the primary shell; the Bash tool is available for POSIX scripts. Installed: git, node 24, pnpm 10, docker, gh (authenticated). Not installed: terraform, psql.

Local Postgres/PostGIS and Redis run in Docker. Never point local development at a shared database.

## Conventions

Conventional commits. One vertical slice per feature branch. All changes via PR with green checks. Protected `main`.

Secrets go in the cloud secret manager and `.env.local` — never committed, never in frontend bundles, never in PR jobs.

Two env files, not one: the repository-root `.env` is the API's and the worker's; `apps/web/.env.local` is the web app's. The split is deliberate — the web app is the only process a browser can reach, so it holds no database credentials at all. Each has an `.env.example` beside it. Note that `.gitignore` ignores `.env.*` and negates only `!.env.example`, so an example file named anything else is silently untracked.

Migrations use expand-and-contract. Every migration states data impact and a rollback/roll-forward note, and has a test.

Ask before adding a dependency that duplicates something we already have.
