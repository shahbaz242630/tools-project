# 0014. Prisma lives in a package, and migrations ship as their own image

- **Status:** Accepted
- **Date:** 2026-07-28
- **Relates to:** BRD §4.2, §15 — builds on [0006](0006-compose-connection-strings-at-runtime.md), [0009](0009-self-hosted-vps-with-off-box-backups.md), [0012](0012-immutable-image-tags-and-compose-deploys.md)

## Context

Phase 1 needs a database. Three questions had to be answered before any schema existed: where the ORM lives, how the schema reaches a running environment, and what Prisma 7 actually requires — because it differs substantially from Prisma 6, and from most documentation still in circulation.

A compatibility gate was run first, per the lesson from the NestJS and Next.js slices. It found four things that change the design:

1. **`url` is not permitted in `schema.prisma`.** Connection settings live in `prisma.config.ts`.
2. **The client requires a driver adapter.** Ours is `@prisma/adapter-pg`, over the same `pg` driver the PostGIS raw queries will use (BRD §4.2).
3. **The generator emits TypeScript source**, not compiled JavaScript. It joins our build rather than sitting inertly in `node_modules`.
4. **`env('DATABASE_URL')` throws while `prisma.config.ts` is being loaded**, which breaks `prisma generate` — a command needing no database — and therefore breaks every Docker build, since images correctly carry no credentials.

The gate also confirmed one thing was no longer a problem: with driver adapters the client uses a WASM query compiler, so the old exercise of matching `linux-musl-openssl` binary targets is gone for the _client_. It is emphatically not gone for the migration CLI.

## Decision

**Prisma lives in `packages/database`.** The schema, the migrations, the generated client and the client factory. Not in `apps/api`: the worker needs database access too, and the schema needs exactly one home.

**The generated client is not committed.** It is regenerated by the root `prepare` script on install and by `build`, and is excluded from prettier, ESLint, coverage and the invariant checker — the last of which matters because the generated code contains `process.env`.

**Migrations ship as their own image**, `migrations`, published alongside `api`, `worker` and `web` and tagged with the same commit SHA. `scripts/deploy.mjs` runs it as a one-off container before bringing the stack up, and a non-zero exit aborts the deploy with the previous release untouched.

**The migrations image does not use the pnpm workspace.** It installs the Prisma CLI directly with npm and copies in only `prisma/` and `prisma.config.ts`. This is ugly and it is deliberate — see below.

**`prisma.config.ts` composes the connection URL from parts** and percent-encodes them, duplicating the rule in `@platform/config` because that package is not reachable from the migrations image. This is the single accepted copy of that logic.

## Consequences

The schema arrives as a versioned artefact that cannot disagree with the code expecting it, because both are tagged with the same commit.

Rolling the application back after a migration stays safe, provided migrations remain expand-and-contract. That is not a nicety: a migration that drops or narrows a column in the same release that stops using it makes the previous image unrunnable, and rollback — the thing ADR 0012 exists to guarantee — silently stops working. BRD §15 already requires expand-and-contract; this is the mechanism that makes the requirement load-bearing.

**The migrations image is about 600 MB**, because `npm install prisma` is not small. It is pulled once per release and runs once per deploy, so the cost is bandwidth on a box that has plenty of time, not memory on one that does not. Worth slimming if it ever becomes annoying.

**Two copies of the URL-encoding rule now exist.** ADR 0006 exists to prevent exactly that, and this is a deliberate exception with a stated reason rather than an oversight. Both are commented to point at the other.

**Generated code is invisible to the tooling**, which is right for prettier and ESLint and slightly uncomfortable for the invariant checker — a rule violation inside generated code would not be caught. Acceptable: we do not write it, and Prisma does not have our invariants.

## Alternatives considered

**Prisma inside `apps/api`.** Simplest today and wrong by the second consumer. The worker will need database access, and a schema that lives inside one application is a schema two applications fight over.

**Running migrations from the API container on startup.** Very common, and it fails badly with more than one replica or during a rolling deploy: several containers race to apply the same migration. It also couples "the app started" to "the schema changed", so a migration failure looks like a crash loop.

**Running migrations from the box's checked-out repository.** The box has the repo for its compose files, so this is tempting. Rejected because it needs `node_modules` on the box, which means the box builds — exactly what ADR 0012 forbids, and for the same reason: the running schema and the tagged commit could then diverge.

**Building the migrations image from the workspace with `pnpm deploy`.** Tried first, and abandoned after it produced an image that could not run. `pnpm deploy` does not carry a devDependency's transitive packages, so `@prisma/engines` was absent; the schema engine is a native binary its postinstall fetches, which `--ignore-scripts` skips anyway. Prisma then tries to download it lazily at first use, and the read-only runtime filesystem makes that fail — reporting the binary as _missing_ rather than as undownloadable, which points the investigation in entirely the wrong direction. A plain `npm install` runs the postinstall and bakes the engine in.

**Passing `DATABASE_URL` from the compose file.** Rejected: compose can only concatenate, and the password we tell operators to generate with `openssl rand` contains `/`, `+` and `=`. An unencoded `/` terminates the URL's authority section, so the connection quietly addresses a different database. Verified by deploying with a throwaway password containing every URL metacharacter that matters — a slash, an at sign, a colon, a plus and an equals — which connects only because the parts are percent-encoded. The literal is deliberately not written here: a credential-shaped string in a public repository trips secret scanners, and an alert everyone learns to wave through is worse than no alert.

## What would change this

If Prisma ships a slim, self-contained migration runner, the 600 MB image and the npm install both go away.

If `@prisma/config` gains a way to resolve an env variable lazily, `prisma.config.ts` gets simpler.

If a second application ever needs a _different_ schema — a genuinely separate bounded context with its own database — this package stops being one thing and the decision needs revisiting.
